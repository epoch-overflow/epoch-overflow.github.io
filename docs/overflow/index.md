# 時刻の桁あふれ問題 一覧

時刻や日付を決まった桁数（ビット数）で表している限り、いつか必ず表せる範囲の端に達します。2038年問題はその代表例ですが、ほかにも同じ種類の問題があります。

| 名称 | 時期（UTC） | 原因 |
|---|---|---|
| 2000年問題（Y2K） | 2000-01-01 | 西暦を下2桁（10進2桁）で保存 |
| GPS週番号ロールオーバー（1回目） | 1999-08-22（GPS時刻） | GPS航法メッセージの週番号が10ビット（1024週） |
| GPS週番号ロールオーバー（2回目） | 2019-04-07（GPS時刻） | 同上 |
| Y2K22（Exchange Server の障害） | 2022-01-01 | 日時を `yymmddHHMM` 形式の整数にして32ビット符号付き整数に格納 |
| NTP の時刻の周回（era 0 の終わり） | 2036-02-07 06:28:16 | NTP タイムスタンプの秒の部分が、1900年起点の32ビット符号なし整数 |
| **2038年問題（Y2K38）** | **2038-01-19 03:14:07** | **UNIX時間を32ビット符号付き整数で保存** |
| GPS週番号ロールオーバー（3回目） | 2038-11-21（GPS時刻） | 週番号が10ビット（1024週） |
| 2106年問題 | 2106-02-07 06:28:15 | UNIX時間を32ビット**符号なし**整数で保存 |

## 共通点

- 時刻を「ある基準時点からの経過量」として、固定幅の整数で表している
- 上限に達すると、値が基準点（またはその前）に巻き戻る
- 原因は値の格納方法にあるので、外から見ても分かりにくい
