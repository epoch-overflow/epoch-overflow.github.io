# 2038年問題とは

## 概要

多くのコンピュータシステムは、時刻を「**1970年1月1日 0時0分0秒（UTC）からの経過秒数**」で表しています。この基準の時刻を **UNIXエポック**、経過秒数を **UNIX時間** と呼びます。

この秒数を**32ビットの符号付き整数**で保存していると、表せる最大値は 2<sup>31</sup> − 1 = 2,147,483,647 秒です。これは次の時刻にあたります。

| | UTC | 日本時間（JST） |
|---|---|---|
| 表せる最後の時刻 | 2038-01-19 03:14:07 | 2038-01-19 12:14:07 |
| 1秒後に「巻き戻る」先 | 1901-12-13 20:45:52 | 1901-12-14 05:45:52 |

最大値を1秒でも超えると値が負に反転し（**桁あふれ**、オーバーフロー）、システムからは**1901年12月**に戻ったように見えます。

## 何が起きるのか

具体的な症状はシステムによって違います。例えば次のようなことが考えられます。

- 日付の表示や記録がおかしくなる（1901年や1970年になる）
- 時刻の前後比較が逆転し、タイマーやタイムアウト、有効期限の判定が誤作動する
- 証明書やライセンスの期限切れ判定を誤る
- 例外やエラーで処理が止まる

## 「2038年になってから」では遅い

2038年問題は、**未来の日付を扱う処理**では2038年より前に表に出てきます。例えば次のようなケースです。

- 30年ローンの満期日、長期保守契約、長期の有効期限の計算
- 「現在時刻 + 非常に長いタイムアウト」の計算

## 2000年問題との違い

| | 2000年問題（Y2K） | 2038年問題（Y2K38） |
|---|---|---|
| 原因 | 西暦を下2桁で保存していた | 経過秒数を32ビット符号付き整数で保存していた |
| 場所 | 主にアプリケーションのデータ形式 | OS・言語ランタイム・ライブラリ・ファイル形式・通信プロトコルなど下位層にも及ぶ |
| 見つけやすさ | 日付フィールドとして目に見えることが多い | 整数型の中に埋もれていて、見ただけでは分かりにくい |

詳しい仕組みは[次のページ](mechanism.md)で説明します。
